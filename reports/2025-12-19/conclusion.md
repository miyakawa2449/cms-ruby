# 第1部：12月17日 — 「動かす」から「安定させる」へ

## 転換点としての一日

12月17日は、このプロジェクトにとって転換点となる一日だった。本番環境が「動く」状態から「安定して動く」状態へと進化した日である。

朝、Docker環境でのActive Storage URL問題から始まり、夜にはMy Storyページの完全な動作確認まで。13回のコミットは、単なるバグ修正の積み重ねではなく、本番環境で信頼性高くサービスを提供するための基盤構築だった。

## 3つの重要な転換

### 1. 「動く」から「確実に動く」へ

deploy.shの大幅な拡張（189行 → 621行）は、単なるスクリプトの肥大化ではない。これは「祈りながらデプロイ」から「確信を持ってデプロイ」への転換を意味する。

```bash
# Before: 祈りのデプロイ
./scripts/deploy.sh
# 動け...動いてくれ...

# After: 確信のデプロイ
./scripts/deploy.sh --keep-ssl --recreate
# 環境変数チェック ✓
# コンテナ順次起動 ✓
# ヘルスチェック ✓
# 自動診断レポート ✓
```

エラーが起きた時に「なぜ？」ではなく「これが原因」とわかる仕組み。それが本番運用の安心感を生む。

### 2. SDK vs SMTP：正解は「ユーザーが決める」

AWS SESの実装で、興味深い往復があった。

1. **最初**: SDK方式で実装
2. **LoadError発生**: SMTP方式に緊急切り替え
3. **最終決定**: ユーザー指示でAPI方式に復帰

技術的には両方正解だった。SMTPはシンプルで確実、APIは機能豊富で監視しやすい。でも最終判断はユーザーが下した。

この経験は重要な教訓を残した。**技術選択において「正解」は一つではない**。どちらを選ぶかは、そのプロジェクトの文脈、運用方針、将来計画によって決まる。AIが提示できるのは選択肢と各々のトレードオフ。決断は人間の仕事だ。

### 3. Rails 7 + Turbo：過去を捨てる勇気

```erb
<!-- 過去のパターン（Rails 6以前） -->
<%= link_to "削除", path, method: :delete, confirm: "本当に？" %>

<!-- 現在のパターン（Rails 7 + Turbo） -->
<%= button_to "削除", path, method: :delete,
    data: { turbo_confirm: "本当に？" } %>
```

たった数行の変更だが、これを見つけるまでに403エラーと格闘した。新しいフレームワークは新しい作法を要求する。古い知識に固執すると、簡単な問題が難問に見える。

## 印象的だった瞬間

### polymorphic_urlの落とし穴

Service層で`polymorphic_url`を呼んだ瞬間、NoMethodErrorが返ってきた。

「なぜ動かない？コントローラーでは動くのに...」

答えは簡単だった。`polymorphic_url`はコントローラーとビューに自動でincludeされるヘルパー。Serviceクラスには含まれない。

フレームワークの「魔法」に慣れすぎると、その魔法が効かない場所で困惑する。今日、魔法の仕組みを一つ理解した。

### 90行のインラインJS削除

My Storyフォームには90行のインラインJavaScriptが埋め込まれていた。動いてはいた。でも読みづらく、Turbo Driveと相性が悪い。

Stimulusコントローラーに移行したことで：
- コードの場所が明確に
- 再利用可能に
- テスト可能に
- Turbo完全対応

技術負債の解消は、新機能追加より地味だが、長期的な生産性に大きく寄与する。

## 17日のまとめ

Claude Codeとの協働で実感したのは、**AIは「広く」考え、人間は「深く」判断する**という役割分担の重要性だ。

AWS SESの方式選択も、Rails 7への対応も、AIが複数の選択肢を提示し、人間がビジネス文脈を考慮して決断した。この協働パターンが、一日で13件もの課題を解決する原動力となった。

# 第2部：12月18日 — MVP完成前夜、そして発信へ

## 二つの軸で進めた一日

18日の特徴は、技術的な仕上げ作業と並行して、この開発体験をブログ記事として発信する準備を進めたことだ。「作る」と「伝える」を同時に行う。それは、単なる開発プロジェクトから「知見を共有するプロジェクト」への転換を意味した。

### 軸1: セキュリティと分析基盤の完成

#### Google Tag Managerの統合

管理画面からGTM IDを設定できる仕組みを実装した。空欄なら何も出力しない。シンプルだが、運用を考えた設計だ。

ところが、GTMのスクリプトがCSPによってブロックされた。

CSPの設定を見直し、GTM、GA4、Microsoft Clarityを許可。ここで興味深い発見があった。**CSP設定が想定していた場所になかった**のだ。

`config/initializers/content_security_policy.rb`を修正しても効果なし。grepで探すと、実際は`application_controller.rb`で設定されていた。

フレームワークの「あるべき姿」と「実際の実装」は異なることがある。この教訓は、他のプロジェクトでも役立つだろう。

#### Devise認証の強化

セキュリティ三点セット：
- **Registerable削除**: 誰でも管理者登録できる穴を塞ぐ
- **Lockable**: 5回失敗で1時間ロック
- **Timeoutable**: 30分無操作でセッション切れ

個人CMSだからといって、セキュリティをおろそかにはしない。これは自分のためだけでなく、将来このCMSを販売する可能性を見据えた判断だ。

#### Contact暗号化

お問い合わせフォームの個人情報をActive Record Encryptionで暗号化した。

ここで問題が発生した。既存の平文データを暗号化されたデータとして読もうとして500エラー。

解決策は`support_unencrypted_data = true`の設定。既存データを壊さず、新規データから暗号化を適用できる。本番環境での段階的移行において重要なテクニックだ。

### 軸2: ブログ記事の準備

技術的な作業と並行して、この3週間の開発体験をブログ記事にまとめる準備を進めた。

#### 「人間3：AI7の黄金比」

この開発を通じて見えてきた協働パターン：
- **人間（30%）**: ビジョン・判断・責任
- **AI（70%）**: 実装・調査・文書化

91ファイル、3,515行のコードが生成されたが、私が手で書いたコードはほぼゼロ。でも、価値の源泉は「どのコードを書くか」を決めた判断にある。

#### 印象的なエピソードの抽出

3週間を振り返って、ブログで語るべきエピソードを整理した：

1. **ルーター買い替え騒動**: bundle installのエラーを、環境変数1行で解決
2. **Docker再起動の威力**: 8つの技術的仮説より、まず再起動
3. **Phase境界の死守**: AIの「実装したい欲」を制御することの価値

これらは単なる技術的解決ではない。**人間とAIの協働における役割分担**の具体例だ。

## Context7 MCPとの出会い

18日から新しいツールが加わった。Context7 MCPだ。

最新のドキュメントを取得し、ベストプラクティスを確認できる。Deviseの設定、Active Record Encryptionの使い方、meta-tags gemの推奨設定—すべてContext7で確認してから実装した。

AIが「知っている」情報だけでなく、「最新の」情報にアクセスできる。これは品質向上に大きく寄与した。

## 表記揺れという地味な問題

「Service」なのか「Services」なのか。

DB、アンカーリンク、ファイル名、管理画面フォーム—すべてで表記が揺れていた。一つひとつは小さな問題だが、放置すると将来のメンテナンスで混乱を招く。

一括で「services」に統一。こういう地味な作業も、MVPの品質を支える重要な仕事だ。
