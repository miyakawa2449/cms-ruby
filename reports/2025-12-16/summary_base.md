# Claude CodeとSE/PMエンジニアの協働パターン分析
作成日: 2025-12-16
目的: Claude Codeを利用したCMS開発を通じて、上流工程専門家がどうClaude Codeを活用すれば楽になるかを分析

## 分析対象期間
2025-11-28 〜 2025-12-15（約2週間半）

## プロジェクト概要
- シニアエンジニアの技術発信・ポートフォリオサイト開発
- Ruby on Rails 8.1.1 + PostgreSQL 17 + Tailwind CSS
- Phase 1（設計）〜 Phase 3（実装）〜 デプロイまで

## インタラクションパターン（初期分析）

### 1. ユーザー介入のタイミングと内容

#### 1.1 方向性の軌道修正
- **事例**: Phase 1でプロトタイプにAPI実装しようとした際
- **ユーザー指摘**: 「時期尚早、設計フェーズを完了させることが重要」
- **結果**: 適切な設計書作成に集中し、実装時の迷いを削減

#### 1.2 技術的判断・決定
- **事例1**: Rails 8.0非対応Gemの対処
- **ユーザー判断**: annotate → annot8採用、redis-rails除外
- **事例2**: マイグレーション複雑化問題
- **ユーザー判断**: Phase 1再設計 vs 継続の選択権提示

#### 1.3 問題切り分けの指示
- **事例**: Ruby 3.4.7のbundle installネットワークエラー
- **ユーザー行動**: 別環境でのテストを実施
- **結果**: ルーター問題ではなくRuby/macOS互換性問題と判明

### 2. Claude Codeが効果的だった場面

#### 2.1 包括的な設計・ドキュメント作成
- **成果物**: 
  - 17画面のプロトタイプ（HTML/CSS）
  - 9つの設計書（DB、API、統合設計）
  - 20のマイグレーションファイル
- **効率性**: 短期間で網羅的な設計を完成

#### 2.2 問題分析と原因特定
- **事例**: マイグレーション複雑化の分析
- **Claude Code成果**:
  - Rails 8.0新機能の理解不足
  - PostgreSQL環境差異
  - 設計書間の不整合
  - Devise統合の曖昧性
  - 5つの根本原因を体系的に整理

#### 2.3 ドキュメント自動更新・整合性確保
- **事例**: Phase 2C完了時
- **更新対象**: CLAUDE.md、README.md、TOMORROW_TASKS.md、spec.md、phase_plan.md
- **効果**: プロジェクト状況の正確な把握、次セッションの効率化

### 3. 協働パターンの特徴

#### 3.1 役割分担の明確化
- **Claude Code**: 実装・詳細設計・技術調査・問題分析
- **ユーザー**: 戦略判断・方向性決定・品質基準設定

#### 3.2 相互補完的な作業
- Claude Codeが実装に走りがちな時、ユーザーが全体視点で軌道修正
- ユーザーの大まかな指示を、Claude Codeが具体的な実装に展開

#### 3.3 レポートによる状況可視化
- 日次レポート作成で進捗と課題を明確化
- 次の判断材料を提供し、意思決定を支援

## インタラクションパターン（詳細分析）

### 4. 問題解決パターン

#### 4.1 環境問題の解決プロセス
- **事例**: Docker環境での500エラー（12/13）
- **Claude Codeの試み**: 8つの技術的解決策を網羅的に実施

- **結果**: 16時間稼働のコンテナ再起動で即座に解決
- **学び**: 複雑な解決策より基本的な対処が有効な場合がある

#### 4.2 実装詳細の具体化
- **事例**: セクション管理実装（12/5）
- **ユーザー要求**: 「8つの異なるセクション対応」
- **Claude Code実装**:
  - JSONBマイグレーション
  - セクション別カスタムフォーム
  - Strong Parameters安全化
- **効果**: 抽象的な要求を具体的な技術実装に展開

#### 4.3 UI/UXフィードバック対応
- **事例**: ポートフォリオUI修正（12/12）
- **ユーザー指摘**: スクリーンショットで具体的な問題箇所を指示
- **Claude Code対応**: 
  - Hero sectionのレイアウト修正
  - 重複テキスト削除
  - レスポンシブ対応
- **特徴**: ビジュアルベースのフィードバックに即座対応

### 5. エラー処理と品質管理

#### 5.1 エラーの段階的切り分け
- **パターン**: エラー発生 → 仮説立案 → 検証 → 原因特定
- **Claude Codeの強み**: 網羅的な仮説リストアップと技術的検証
- **ユーザーの強み**: 経験に基づく優先順位付けと判断

## SE/PM向けベストプラクティス

### 1. 効果的な指示の出し方

#### 1.1 フェーズを明確にする
- **良い例**: 「Phase 1は設計のみ。実装は行わない」
- **効果**: Claude Codeが適切なスコープで作業を進める
- **ポイント**: 上流・下流の境界を明確に伝える

**【対話例：Phase境界の明確化】**
```
Claude Code: 「プロトタイプが完成しました！17画面すべて作成完了です。
次はこのプロトタイプにAPI実装を追加していきましょう。
まずは認証エンドポイントから...」

ユーザー: 「ちょっと待って。今はまだPhase 1の設計フェーズだよね？」

Claude Code: 「はい、Phase 1です」

ユーザー: 「Phase 1は設計と仕様策定のみ。実装は行わない。
プロトタイプへのAPI実装は時期尚早。
まずはAPI設計書を作成して、DB設計との整合性を確認して」

Claude Code: 「理解しました。実装ではなく設計に集中します。
API設計書とエンドポイント一覧を作成し、
既存のDB設計との統合分析を行います」

ユーザー: 「そうそう。設計フェーズを完全に終わらせてから実装に入る。
その方が手戻りが少ない」
```

#### 1.2 品質基準を最初に設定
- **実践例**: CLAUDE.mdに品質基準を明文化
  - メソッド20行以内
  - クラス100行以内
  - 重複は3回まで
- **効果**: 自動的にリファクタリングが実行される

#### 1.3 ビジュアル素材の活用
- **スクリーンショット**: UI問題の具体的指摘
- **ワイヤーフレーム**: 期待する画面構成の共有
- **効果**: 言語化しづらい要求を正確に伝達

**【対話例：スクリーンショットベースのUI修正】**
```
ユーザー: 「Heroセクションがおかしい。スクリーンショット見て
[screenshot.png添付]」

Claude Code: 「スクリーンショットを確認しました。以下の問題が見つかりました：
1. スクロールを促すテキストがCTAボタンと重なっている
2. レイアウトが崩れている」

ユーザー: 「そう。あとAboutセクションで"About Me"が2回出てる」

Claude Code: 「修正します：
- Hero section: flex layoutを適用してCTAボタンの重複を解消
- About section: 重複している見出しを削除
- Works section: 統計エリアが未完成のようなので一時非表示にしますね」

ユーザー: 「いいね。ビジュアルで見せると話が早い」

Claude Code: 「修正完了しました。モバイル・タブレット表示も確認済みです」
```

### 2. 問題解決の協働パターン

#### 2.1 基本から始める指示
```
❌ 悪い例: 「500エラーを解決して」
✅ 良い例: 「まずDocker再起動。それでダメなら順に調査」
```

**【対話例：Docker 500エラーの解決】**
```
ユーザー: 「本番環境で500エラーが出てる。管理画面は入れるけどメインページがダメ」

Claude Code: 「エラーの原因を調査します。以下の8つの可能性を順に検証します：
1. データベース接続の問題
2. 環境変数の不足
3. アセットパイプラインの問題
4. ビューファイルのレンダリングエラー
5. ヘルパーメソッドの未定義...」

ユーザー: 「待って。コンテナどれくらい動いてる？」

Claude Code: 「確認します... 16時間前から稼働しています」

ユーザー: 「じゃあまずdocker-compose down して up -d してみて」

Claude Code: 「Dockerを再起動します... 完了。確認したところ、500エラーが解消されました！」

ユーザー: 「やっぱりね。長時間稼働で状態がおかしくなってたんだ。複雑な解決策の前に基本的なことから試すのが大事」
```

#### 2.2 経験則の共有
- **例**: 「Rails 8の新機能に注意」「PostgreSQL Alpineは機能制限あり」
- **効果**: Claude Codeが適切な技術選択を行える

**【対話例：Ruby環境問題の解決】**
```
Claude Code: 「bundle installでハッシュエラーが発生しています。
ネットワークの問題の可能性があります。
ルーターの設定を確認してみてください」

ユーザー: 「別のネットワークでも試してみたけど、同じエラーが出るよ」

Claude Code: 「同じエラーが再現するということは、
ネットワーク環境の問題ではなさそうですね」

ユーザー: 「Ruby 3.4.7使ってるんだけど、Mac特有のエラーがあるかもしれない。
ネットで同じ現象で解決した事例を探して」

Claude Code: 「調査しました。Ruby 3.4系でmacOSでの問題を発見しました。
Happy Eyeballs v2という新機能がSSL接続で問題を起こすケースがあるようです。
解決策として、環境変数 RUBY_TCP_NO_FAST_FALLBACK=1 を設定する方法が見つかりました」

ユーザー: 「それ試してみて」

Claude Code: 「環境変数を設定してbundle installを実行... 成功しました！
220 gems がインストールされました。.zshrcに永続的に設定を追加しておきますね」

ユーザー: 「やっぱり最新バージョン特有の問題だったか。
ルーター買い替えなくてよかった」
```

## 結論

Claude Codeは単なるコーディング支援ツールではなく、SE/PMの**拡張知能**として機能する。適切な指示と役割分担により、上流から下流まで一貫した開発支援が可能。

特に効果的な活用シーン：
1. **設計の高速化**: プロトタイプと設計書の自動生成
2. **実装の効率化**: 定型作業の自動化
3. **問題解決の迅速化**: 網羅的な調査と原因特定
4. **品質の維持**: 自動リファクタリングと基準遵守

成功の鍵は「**人間の判断力**」と「**AIの処理能力**」の最適な組み合わせにある。
