## 1. 背景と目的

現在の管理画面の防御は「秘密URL（難読化）+ パスワード + TOTP 2FA」の組み合わせだが、次の課題がある:

1. 秘密URL機構（Resolver/Updater/ローテーション/履歴/通知/RouteReloader）は**7コンポーネントの維持コスト**に対し、防御効果は「ログイン画面の発見を遅らせる」に留まる
2. TOTP 2FAに**運用上の不安定さ**が報告されている（§3で調査）
3. パスワードという「漏れうる共有秘密」が依然として存在する

パスキー（WebAuthn）は**フィッシング不能・総当たり不能・パスワード漏洩の概念なし**という性質で、これらを根本から解決する。UXもFace ID/Touch IDタッチで完了し向上する。

## 2. 用語と前提（重要な概念）

- **パスキー**: 公開鍵暗号のペア。**公開鍵のみ本CMSのDBに保存**し、秘密鍵はユーザーのデバイス（のセキュア領域）に保存される
- **同期プラットフォーム**: iCloudキーチェーン（Apple系: iPhone/iPad/Mac）、Googleパスワードマネージャー（Android/Chrome）等が、秘密鍵を同一アカウントのデバイス間で同期する
- **実装は1つ**: WebAuthnはW3C標準であり、Apple用/Google用のコードは存在しない。**1つの実装で全プラットフォームのパスキーが使える**
- **ソーシャルログインとの違い**: 「Appleでサインイン」等のOAuthとは別物。本機能でApple/Googleのアカウント連携は行わない。**Facebook等のソーシャルログインは不要**（2026-07-16 剛さん判断・Claude Code同意: 管理者1名のCMSにOAuth連携を足す意味がなく、パスキーの文脈でFacebookは同期プラットフォームですらない）

## 3. 現状分析: TOTP 2FAの不安定さ調査

### 3-1. コードから確認した事実

| 項目 | 現状 |
|---|---|
| OTP許容ドリフト | **デフォルト値**（前後30秒）。明示設定なし |
| TOTPコードの有効期間 | 30秒（標準） |
| アカウントロック | `maximum_attempts = 5`（Devise lockable）、ロック解除は1時間後 |
| **OTP入力ミスもロック回数にカウントされる** | devise-two-factorはログイン失敗として扱うため、**パスワードが正しくてもOTPを5回ミスすると1時間ロック** |
| セッションタイムアウト | 30分（timeoutable）。切れるたびにパスワード+OTPの再入力 |
| otp_secretの暗号化 | Active Record Encryption（Rails標準）。鍵はcredentials管理 |

### 3-2. 症状の確定（2026-07-16 剛さん回答）

**「2FAでログインしていても、セッションタイムアウト（30分）より短い間隔で再ログインを求められることがある」**

### 3-3. 症状に合致する原因仮説（優先順）

セッションクッキーは24時間有効（`session_store.rb`）のため、30分より短い再ログイン要求は以下のいずれかの可能性が高い:

1. **複数デバイス間のrememberトークン無効化**: Deviseのrememberableはトークンをユーザーごとに1つしか持たない。iPhoneとMacの両方で「ログイン状態を保持する」を使っていると、**片方でログアウトした瞬間にもう片方のremember cookieも無効化**され、他方が「突然ログインを求められる」。複数デバイス利用の管理者に典型的な症状
2. **timeoutableの誤解**: 30分は「最後の操作から」のアイドル時間。画面を開いたまま30分放置→操作、で再ログインになるため、体感では「もっと短い」と感じることがある
3. **iOS SafariのITP（トラッキング防止）によるクッキー削除**: iPhoneでの利用時、Safariが一定条件でクッキーを消すことがある
4. **管理URL変更による強制ログアウト**（7/15にパス変更を実施した際の1回性のもの。恒常的原因ではない）

### 3-4. 調査・是正アクション（実装フェーズで実施）

- [ ] 本番サーバーの時計ズレ確認: `docker compose exec portfolio-web date && date` の比較
- [ ] `otp_allowed_drift` を明示設定（前後60秒に拡大）
- [ ] ログでロック発生・強制ログアウトの履歴確認
- [ ] 仮説1の検証: 複数デバイスでremember me使用時のログアウト連鎖を再現テスト
- [ ] **是正**: `:timeoutable` の廃止（§5参照・剛さん決定）により仮説2は解消。仮説1はデバイス別rememberトークン化（Devise標準外のため対応可否を実装時に判断）または「パスキー移行によりログインコスト自体が激減する」ことで実質解消

## 4. スコープ

### Phase A（本フェーズで実装）
- パスキーの登録・一覧・削除（管理画面のセキュリティ設定）
- パスキーによるログイン（**パスワード+2FAとの並行運用**。どちらでも入れる）
- リカバリー設計（§6）
- 2FA不安定さの調査と是正（§3-4）
- **セッションタイムアウトの廃止**（2026-07-16 剛さん決定: `:timeoutable` を外す。セッションはクッキー有効期限24時間+remember me 2週間で管理）

### Phase B（Phase A安定稼働の確認後、別コミット群で実施）
- **パスワードレス化**（2026-07-16 剛さん決定: **採用する**。Phase Aで並行運用→パスキーでの運用が安定したことを確認してから、パスワード+OTPログインを無効化する。切替はENVまたは設定で可逆にし、締め出し時はサーバーコンソールから復旧可能とする）
- 管理URLローテーション機構の廃止（RotationJob/Updater/AdminPathMailer/履歴画面。**Resolver+ENV設定+RouteReloaderは残す**=パス自体の設定機能は維持）

### 非スコープ
- ソーシャルログイン（Facebook/Google/Appleアカウント連携）— §2の判断どおり不要
- 公開側（ブログ読者向け）の認証 — 存在しない
- マルチ管理者対応 — S2（ただしテーブル設計はadmin_user_idを持ち、S2でそのまま複数人に対応できる形にする）

## 5. 機能要件

### FR-1: パスキー登録
- 管理画面「セキュリティ設定」にパスキー管理セクションを追加
- 登録時に**ニックネーム**を付与（例: 「iPhone」「Mac Chrome」）。未入力時はブラウザ情報から自動命名
- 1管理者につき**複数パスキー登録可能**（上限10）
- 登録には現在のセッション（ログイン済み）+ **パスワード再入力**を要求（既存の`verify_password`パターン踏襲）

### FR-2: パスキーログイン
- ログイン画面に「パスキーでログイン」ボタンを追加（メール入力不要のdiscoverable credential方式を第一候補とし、実装時にブラウザ互換で判断）
- パスキー成功時は**OTP入力を要求しない**（パスキー自体が多要素: 所持+生体）
- 従来のパスワード+OTPログインは**そのまま併存**（Phase A）

### FR-3: リカバリー設計（本仕様の核心）
- **推奨構成**: Apple系デバイスで1つ + Google系（Chrome/Android）で1つ = 異なる同期プラットフォームに2系統
- パスキーが1つしか登録されていない間は、管理画面に**警告バナー**を常時表示（「もう1つのプラットフォームでパスキーを追加してください」）
- 最後の1つのパスキーを削除する操作は、パスワード+2FAが有効な場合のみ許可（完全な締め出し防止）
- **Phase Bのパスワードレス有効時は、パスキーが2つ以上ないとパスワードレス化できない/最後の2つは削除不可**とする（締め出しの構造的防止）
- 最終防衛線: パスワード+2FA（Phase Aでは常に有効）、それも失われた場合はサーバーのコンソールから復旧（手順をドキュメント化）

### FR-4: 管理・監査
- パスキー一覧に「最終使用日時」を表示
- 登録・削除時にメール通知（既存のTwoFactorAuthMailerパターン踏襲）+ Slack通知
- ログイン成功時に使用したパスキーの`last_used_at`と`sign_count`を更新

## 6. 技術設計

### gem選定
- **webauthn-ruby（`webauthn` gem）**: Cedarcode製、WebAuthn標準の実装として最も実績がある。devise-passkeysは若く採用しない。Deviseへは**カスタムWardenストラテジー**で統合（devise-two-factorと同じ統合パターン）

### データモデル（新テーブル: `passkey_credentials`）
| カラム | 型 | 制約 |
|---|---|---|
| admin_user_id | bigint | NOT NULL, FK |
| external_id | string | NOT NULL, UNIQUE（WebAuthnのcredential ID、Base64） |
| public_key | string | NOT NULL |
| nickname | string | NOT NULL |
| sign_count | bigint | NOT NULL, default 0（クローン検知用） |
| last_used_at | datetime | |
| created_at/updated_at | | NOT NULL |

- AdminUserに `webauthn_id`（string）カラム追加（WebAuthnのユーザーハンドル）

### 設定
- RP ID（Relying Party ID）= ドメイン。`APP_HOST` から導出し、developmentは `localhost`
- **HTTPS必須**（本番は対応済み。localhostは例外として動作する）

### セキュリティ考慮
- challengeはセッションに保存し一度きり使用
- `sign_count` の逆行を検知したら該当パスキーを無効化しメール通知（クローン検知）
- 登録・削除はrack_attackのレート制限対象に追加

## 7. 受け入れ基準

> **補足（2026-07-16実機検証での学び）**: iCloudキーチェーンのパスキーは1つでApple全デバイス（Mac Safari/iPhone/iPad）をカバーする。同一保管庫への二重登録はWebAuthnの除外リストが正しく拒否するため、「2系統」とは **iCloudキーチェーンに1つ + Googleパスワードマネージャーに1つ** を指す（デバイスごとではない）

1. Apple系: パスキーを登録し、Mac（Touch ID）とiPhone（Face ID・同じiCloud同期鍵）でログインできる
2. Google系: Chromeの保存先を「Chromeプロファイル/Googleパスワードマネージャー」にして登録し、ログインできる
3. パスキー登録後も、従来のパスワード+OTPでログインできる（並行運用）
4. パスキーログイン時にOTP入力を求められない
5. パスキー1つの状態で警告バナーが表示され、2つ登録すると消える
6. 最後のパスキー削除の制約が機能する
7. 登録・削除でメール+Slack通知が届く
8. 全specグリーン + 新規フローのrequest spec/システムspec（WebAuthnはテスト用のfake client=webauthn gem付属のFakeClientを使用）
9. 2FAドリフト設定の明示化と、不安定さ原因の調査結果レポート

## 8. テスト計画（TDD必須領域）

- モデル: PasskeyCredential（バリデーション、sign_count逆行検知、最終パスキー削除ガード）
- リクエスト: 登録チャレンジ発行→検証、ログインチャレンジ→検証、削除、レート制限
- 統合: 登録→ログアウト→パスキーログイン→OTPスキップ確認（FakeClient）
- 回帰: 既存のパスワード+OTPログインが無傷であること（既存128例の認証系spec）

1. 2FA不安定さ調査（§3-3）+ ドリフト明示設定 ← 独立して先行可

## 10. 決定事項（2026-07-16 剛さん回答により確定）

1. 2FA不安定さの症状 = 「タイムアウトより短い間隔での再ログイン要求」→ §3-3の仮説に基づき調査・是正
2. **セッションタイムアウトは廃止**（`:timeoutable` を外す）
3. **パスワードレス化は採用**。進め方: まずPhase A（パスキーとパスワード+2FAの並行運用）で開始 → パスキー運用の安定を確認 → Phase Bでパスワードログインを無効化。「最初はPhase Aでいく」で正しい理解です
