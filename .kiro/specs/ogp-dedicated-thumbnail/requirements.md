# OGP専用サムネイル保存・参照機能 - 要件定義

## 1. 概要

ブログ記事のサムネイル画像について、記事表示用（4:3）とOGP用（1.9:1 = 1200x630）で異なる画角が求められる課題を解決するため、OGP専用画像を別途保存・参照できる仕組みを追加する。

## 2. 背景と課題

### 現状の問題
- 記事サムネイルは4:3（1200x900）でトリミングしている
- OGP生成時に `resize_to_fill: [1200, 628]` が適用され、センタークロップされる
- 意図した画角が維持できず、重要な要素が切れる可能性がある
- Twitter/Facebookなどのソーシャルメディアでは1.9:1の画角が推奨される

### 解決すべき課題
1. 記事表示用とOGP用で異なる画角を両立させる
2. 既存の4:3トリミングフローを維持しつつ、OGP用画像を追加する
3. 管理画面での編集体験を損なわない
4. 既存記事への影響を最小限にする

## 3. ユーザーストーリー

### US-1: 管理者としてOGP専用画像を設定したい
**As a** ブログ管理者  
**I want to** 記事ごとにOGP専用の画像を設定できる  
**So that** SNSでシェアされた際に意図した画角で表示される

**受け入れ基準:**
1.1. 記事編集画面でサムネイル画像をアップロードする際、4:3とOGP用（1.9:1）の両方をプレビューできる  
1.2. 保存時に4:3画像とOGP専用画像が両方保存される  
1.3. OGP専用画像は1200x630ピクセルで保存される  
1.4. 既存の4:3トリミングフローは変更されない

### US-2: 管理者としてOGP画像の有無を確認したい
**As a** ブログ管理者  
**I want to** 記事一覧でOGP画像の設定状況を確認できる  
**So that** どの記事にOGP画像が設定されているか把握できる

**受け入れ基準:**
2.1. 記事一覧画面でOGP画像の有無が視覚的に分かる  
2.2. OGP画像未設定の記事を絞り込める  
2.3. 一括でOGP画像を生成する機能がある（オプション）

### US-3: システムとしてOGP画像を優先的に使用したい
**As a** システム  
**I want to** OGP専用画像が存在する場合はそれを使用する  
**So that** SNSでの表示品質が向上する

**受け入れ基準:**
3.1. OGP専用画像が存在する場合、OGPメタタグでそれを使用する  
3.2. OGP専用画像が未設定の場合、既存の4:3画像から自動生成する（フォールバック）  
3.3. フォールバック時は `resize_to_fill: [1200, 628]` を使用する  
3.4. 画像URLの生成ロジックは `MetaTagsService` に集約される

### US-4: 既存記事のOGP画像を移行したい
**As a** ブログ管理者  
**I want to** 既存記事のOGP画像を一括生成できる  
**So that** 過去の記事もSNSで適切に表示される

**受け入れ基準:**
4.1. 既存記事のサムネイルからOGP画像を自動生成するRakeタスクがある  
4.2. 生成時は4:3画像の中央部分を1.9:1で切り出す  
4.3. 既にOGP画像が設定されている記事はスキップする  
4.4. 実行結果（成功/スキップ/失敗）がログに記録される

## 4. 機能要件

### FR-1: データモデル拡張
- `Article` モデルに `ogp_image` アタッチメントを追加
- Active Storageを使用して画像を保存
- 既存の `thumbnail_image` とは独立して管理

### FR-2: サムネイル編集UI拡張
- 現行のトリミングモーダルを拡張
- 4:3プレビューとOGP用プレビューを並べて表示
- 保存時に両方の画像を生成・保存
- OGP用画像は4:3画像の中央部分を自動切り出し

### FR-3: OGP画像生成ロジック
- `MetaTagsService#article_meta_tags` を拡張
- OGP専用画像が存在する場合はそれを優先
- 未設定の場合は既存ロジックでフォールバック
- 画像サイズは1200x630を維持

### FR-4: 管理画面での表示
- 記事一覧でOGP画像の有無を表示
- 記事編集画面でOGP画像のプレビューを表示
- OGP画像の個別削除が可能

### FR-5: 移行ツール
- 既存記事のOGP画像を一括生成するRakeタスク
- 4:3画像から中央部分を切り出して生成
- 実行結果をログ出力

## 5. 非機能要件

### NFR-1: パフォーマンス
- OGP画像の生成は非同期処理で実行（オプション）
- 画像サイズは最適化される（JPEG品質92%）
- CDN経由で配信される（Active Storage設定に依存）

### NFR-2: 互換性
- 既存の記事表示ロジックに影響を与えない
- OGP画像未設定の記事は従来通り動作する
- 既存のテストが壊れない

### NFR-3: 保守性
- OGP画像生成ロジックは再利用可能な形で実装
- サービスクラスに責務を分離
- テストカバレッジを維持

## 6. 制約事項

### 技術的制約
- Active Storageを使用（既存の画像管理と統一）
- 画像処理はImageMagick/libvipsに依存
- OGP画像サイズは1200x630固定

### ビジネス的制約
- 既存記事の編集は不要（自動生成で対応）
- 管理画面のUI変更は最小限にする
- 段階的なリリースが可能な設計

## 7. 成功指標

- OGP画像が設定された記事の割合: 80%以上
- SNSでのシェア時の画像表示率: 95%以上
- 管理者のサムネイル編集時間: 変化なし
- 既存記事への影響: ゼロ

## 8. 除外事項

以下は本機能の対象外とする:

- 複数のOGP画像バリエーション（1つの記事に1つのOGP画像のみ）
- OGP画像の手動アップロード（4:3画像から自動生成のみ）
- リアルタイムプレビュー機能の大幅な変更
- 他のコンテンツタイプ（My Story、Portfolioなど）へのOGP画像対応

## 9. 依存関係

### 前提条件
- Active Storageが正常に動作している
- ImageMagick/libvipsがインストールされている
- 既存のサムネイル編集機能が動作している

### 影響を受けるコンポーネント
- `app/models/article.rb`
- `app/services/meta_tags_service.rb`
- `app/javascript/controllers/thumbnail_editor_controller.js`
- `app/views/admin/articles/_form.html.erb`
- `app/views/admin/articles/index.html.erb`

## 10. リスクと対策

### リスク1: 既存記事のOGP表示が変わる
**対策:** フォールバックロジックを維持し、段階的に移行

### リスク2: 画像生成処理の負荷
**対策:** 非同期処理化、バッチ処理での生成

### リスク3: ストレージ容量の増加
**対策:** 画像最適化、古い記事の定期的なレビュー
